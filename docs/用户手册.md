# influxdb2tsfile 用户手册

版本：0.1.0（基于 Apache TsFile 2.4.0）

---

## 1. 这个工具是做什么的

`influxdb2tsfile` 是一个命令行工具，把 **InfluxDB 中的时序数据**转换成 **Apache TsFile** 文件：

- 数据源：
  - InfluxDB 1.x（InfluxQL + 用户名/密码）
  - InfluxDB 2.x（走 InfluxQL 兼容接口，使用 API Token）
  - line protocol 文本文件 / 标准输入（离线迁移，实例已下线时使用）
- 目标：TsFile 2.4.0 的 **表模型（table model）**，即「一张表 = 一个 measurement」，tag 变成 TAG 列，field 变成普通字段列，时间戳为原生时间列

典型场景：

1. 阿里云 InfluxDB® 版退市前，把实例里的历史数据整体搬到 TsFile，后续用 TimechoDB / IoTDB / TsFile SDK 继续存储和分析；
2. 自建 InfluxDB 1.x/2.x 退役，需要长期归档为列式文件；
3. 已导出的 line protocol 备份文件，需要转成 TsFile。

工具**不会**修改源库，只用只读的 InfluxQL 查询读取数据，可反复执行。

## 2. 环境与安装

### 2.1 依赖

| 项目 | 版本要求 | 说明 |
| --- | --- | --- |
| JDK | 17 及以上 | 运行与构建都要（TsFile 2.4.0 编译为 Java 17 字节码，低于 17 会报 `类文件具有错误的版本 61.0`） |
| Maven | 3.6 及以上 | 仅构建需要 |
| Apache TsFile | 2.4.0 | 已作为依赖打进 fat-jar，无需单独安装 |

### 2.2 构建

```bash
mvn -DskipTests package     # 只打包，跳过测试
mvn test                    # 运行测试（含内置 mock InfluxDB 的集成测试，不需要真实实例）
```

构建产物：

- `target/influxdb2tsfile-0.1.0.jar`：可执行 fat-jar（含 TsFile、Jackson、picocli 等依赖）
- `target/original-influxdb2tsfile-0.1.0.jar`：不带依赖的瘦 jar，可忽略

### 2.3 运行方式

方式一（推荐，自带内存参数）：

```bash
bin/influxdb2tsfile migrate --help
```

方式二：

```bash
java -Xmx4g -jar target/influxdb2tsfile-0.1.0.jar migrate --help
```

方式三（长任务建议放到后台并保留日志）：

```bash
nohup java -Xmx4g -jar target/influxdb2tsfile-0.1.0.jar migrate ... > migrate.log 2>&1 &
tail -f migrate.log
```

退出码：

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功（`--verify` 校验通过） |
| 1 | 失败：参数错误、连接失败、有工作单元失败、校验不一致 |

日志输出到 **标准错误**（stderr），`discover --json` / `inspect --json` 的结构化输出到 **标准输出**（stdout），便于脚本处理。

## 3. 迁移总览（推荐流程）

```
① discover  ── 探查 schema，确认 work 表名/列名/类型映射，评估工作量
② dry-run   ── 打印迁移计划（工作单元数、切片数），不读数据
③ migrate   ── 正式迁移，生成 *.tsfile 与 manifest.json（可中断、可 --resume 续跑）
④ inspect   ── 查看产物结构、行数、时间范围，并用 --manifest 做行数校验
```

一条完整命令序列（1.x，用户名密码认证）：

```bash
JAR=target/influxdb2tsfile-0.1.0.jar
URL=http://influxdb-host:8086
DB=telegraf
OUT=/data/tsfile/$DB

# ① 探查
java -jar "$JAR" discover --url "$URL" --database "$DB" --username admin --password admin123 --counts

# ② 计划
java -jar "$JAR" migrate --url "$URL" --database "$DB" --username admin --password admin123 \
  -o "$OUT" --time-slice 1d --parallel 4 --dry-run

# ③ 迁移（可反复执行，自动跳过已完成的单元）
java -jar "$JAR" migrate --url "$URL" --database "$DB" --username admin --password admin123 \
  -o "$OUT" --time-slice 1d --parallel 4 --resume --verify

# ④ 校验
java -jar "$JAR" inspect "$OUT" --manifest "$OUT/manifest.json"
```

## 4. 数据映射规则

### 4.1 总览

| InfluxDB 概念 | TsFile 表模型 | 备注 |
| --- | --- | --- |
| database / bucket | 输出目录 | 需要合并多个库时用 `--table-prefix` 区分表名 |
| measurement | table（表名） | 与 measurement 同名（经命名规范处理） |
| tag key | TAG 列（STRING） | 一行的所有 TAG 列取值组成设备 ID（device id），即 InfluxDB 的 series |
| tag value | TAG 列的值 | 同一 measurement 中缺失的 tag 取值写成空字符串 `""`，保证设备 ID 稳定 |
| field key | FIELD 列 | 列类型由 InfluxDB 字段类型决定 |
| field value | FIELD 列的值 | 该行没有这个 field 时写 null |
| point timestamp | 行时间戳（INT64，纳秒） | TsFile 原生时间列，纳秒精度无损 |

一条 InfluxDB 数据点对应 TsFile 中的一行：

```
InfluxDB: cpu,host=host-a,region=cn usage_idle=90.5,cores=8i 1704067200000000000
                    │                     │
TsFile  : 表 cpu 的 TAG 列 host=host-a, region=cn   FIELD 列 usage_idle=90.5, cores=8
              行时间戳 1704067200000000000
```

设备（device）即 series：`(表名, TAG1值, TAG2值, ...)`。同一个设备的数据在 TsFile 中按时间递增排列，并共享一套 chunk group，读取时可以按设备下推。

### 4.2 字段类型映射

| InfluxDB 字段类型 | TsFile 类型 | 说明 |
| --- | --- | --- |
| float | DOUBLE | 默认类型，精度无损 |
| integer | INT64 | `7i` 这类整数，无损 |
| unsigned | INT64 | 无符号整数，超过 INT64 上限（9223372036854775807）会报错 |
| string | STRING | UTF-8 |
| boolean | BOOLEAN | true/false |

tag 列一律为 STRING。

### 4.3 列名规范化

TsFile 表模型对表名/列名是**大小写不敏感**的（内部统一转小写），因此工具在写文件前会做规范化，并把「原始名称 ↔ 实际列名」的对应关系记录在 `manifest.json` 的 `tables[].columns[].source` 中：

| 规则 | 例子 |
| --- | --- |
| 统一转小写 | `UsageIdle` → `usageidle` |
| 非字母数字下划线（含中文以外的符号）替换为 `_`，连续符号合并 | `cpu usage` → `cpu_usage`，`a.b-c` → `a_b_c` |
| 中文（汉字）保留 | `温度` → `温度` |
| 首尾下划线去掉，空名变 `col` | `///` → `col` |
| 保留字 `time` 改名 `time_col` | 避免与 TsFile 时间列冲突 |
| 重名（含大小写不同）加序号 | 同名 tag 与 field：`value`（TAG）+ `value_1`（FIELD） |

不想改名可以加 `--no-sanitize`，此时只做小写处理，其余字符原样保留。

### 4.4 字段类型冲突

InfluxDB 允许同一个 field key 在不同分片里有不同类型（例如早期是 float，后期写入了 string）。这种 measurement 无法直接映射到单列，默认会**跳过该 measurement 并报错**：

```
ERROR skip measurement 'sensor': field 'value' of measurement 'sensor' has more than one data type in InfluxDB;
use --type-conflict text to store it as string, or query it slice by slice with --time-slice
```

三种处理方式：

1. `--type-conflict text`：该字段统一按 STRING 存储（所有取值转成字符串，不丢数据，但数值查询要转型）；
2. `--time-slice` + 分批：把时间范围切小，常能把不同类型限制在不同批次（本工具按批查询，不会跨批次冲突）——注意：如果冲突发生在同一时间范围内仍需方式 1；
3. 源端修复：在 InfluxDB 侧把数据规范化后再迁移。

也可以用 `--field-type value=FLOAT` 强制指定某字段类型（先出现的类型会被强制转换，转换失败会报错）。

### 4.5 稀疏数据

InfluxDB 里同一个 series 的不同时间点可以有不同 field 集合。迁移后这些差异体现为 **null 列值**：TsFile 用 bitmap 标记空值，不额外占数据空间，读出来是 null。示例：

```
cpu,host=b usage=3.5 1704067200000000000        → usage=3.5, count=null, label=null
cpu,host=b usage=3.6,count=7i 1704067260000000000 → usage=3.6, count=7, label=null
```

## 5. 命令参考

四个子命令：`migrate`、`discover`、`lp2tsfile`、`inspect`。任意命令加 `--help` 查看参数。

### 5.1 连接参数（migrate / discover 通用）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-u, --url` | `$INFLUX_URL` | InfluxDB 地址，如 `http://127.0.0.1:8086`；不带协议时按 http 处理 |
| `-d, --database, --bucket` | `$INFLUX_DATABASE / $INFLUX_BUCKET` | 1.x 的 database，2.x 的 bucket |
| `--token` | `$INFLUX_TOKEN` | 2.x 的 API Token（1.x 请使用用户名密码） |
| `-U, --username` / `-P, --password` | `$INFLUX_USERNAME / $INFLUX_PASSWORD` | 1.x 用户名密码 |
| `--org` | `$INFLUX_ORG` | 2.x 组织名（本工具走 InfluxQL 兼容接口，一般不需要） |
| `--rp, --retention-policy` | 库的默认 RP | 1.x retention policy；留空自动探测 |
| `--server-version` | `auto` | `auto / 1 / 2`，用于校验与提示 |
| `--connect-timeout` | `10s` | 连接超时 |
| `--query-timeout` | `300s` | 单次查询等待响应头的超时；超大时间片可调大 |
| `--chunk-size` | `10000` | 每次流式返回的点数，越大网络往返越少 |
| `--log-level` | `info` | `trace/debug/info/warn/error` |

### 5.2 输出与写入参数（migrate / lp2tsfile 通用）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-o, --out` | `.` | 输出目录，不存在会自动创建 |
| `--file-prefix` | 空 | 输出文件名前缀，见第 7 节命名规则 |
| `--table-prefix` | 空 | 表名前缀，如 `--table-prefix telegraf` → 表名 `telegraf_cpu` |
| `--max-file-size` | `1GB` | 单个 tsfile 分片大小上限，超出后滚动新文件；`0` 表示不限 |
| `--max-rows-per-file` | `0`（不限） | 单个分片行数上限 |
| `--batch-size` | `4096` | 每批写入 Tablet 的行数，影响写入吞吐与内存 |
| `--max-buffered-rows` | `200000` | 内存中最多缓存的行数，超过后强制刷盘 |
| `--compression` | LZ4（TsFile 默认） | `UNCOMPRESSED/SNAPPY/GZIP/LZ4/ZSTD/LZMA2` |
| `--memory-threshold` | `64MB` | 单个 chunk group 的内存阈值 |
| `--no-sanitize` | 否 | 列名/表名只转小写，不做符号替换 |
| `--include-tags` / `--exclude-tags` | 全部 tag | 只保留 / 排除指定 tag key（逗号分隔，可重复） |
| `--exclude-fields` | 无 | 不迁移指定 field（逗号分隔） |
| `--field-type` | 无 | 强制字段类型，如 `--field-type usage=FLOAT,temp=DOUBLE` |
| `--type-conflict` | `fail` | 类型冲突策略：`fail` 或 `text` |

提示：**排除 tag 有风险**。tag 是 series 的标识，去掉 tag 后不同 series 的同一时间点会被合并成一行（同名 timestamp 合并、后者覆盖前者）。除非明确知道不会有时间戳重复，否则不要排除 tag。

### 5.3 `migrate`：从 InfluxDB 迁移

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--measurements` | 全部 | 指定 measurement，逗号分隔 |
| `--measurement-regex` | 无 | 正则筛选 measurement（Java 正则） |
| `--ignore-case` | 否 | measurement 名称忽略大小写 |
| `--start` | `1970-01-01T00:00:00Z` | 起始时间 |
| `--end` | `now` | 结束时间（**不含**） |
| `--time-slice` | 无（整段一次查询） | 时间切片长度，如 `1d`、`6h`；每个切片是一个工作单元 |
| `--parallel` | `1` | 并行工作单元数，建议 2~8，与 InfluxDB 承受能力匹配 |
| `--retries` | `1` | 单元失败重试次数 |
| `--resume` | 否 | 读取已有 manifest，跳过已完成单元 |
| `--verify` | 否 | 迁移结束后回读所有分片，比对行数 |
| `--dry-run` | 否 | 只打印计划，不读数据 |
| `--fail-fast` | 否 | 第一个单元失败即停止 |
| `--manifest` | `<out>/manifest.json` | 清单文件路径 |

时间格式支持：

| 写法 | 例子 | 说明 |
| --- | --- | --- |
| RFC3339 | `2024-01-01T00:00:00Z` | 推荐 |
| 日期 | `2024-01-01` | 当天 00:00:00 UTC |
| 相对时间 | `-7d`、`-1h30m`、`+2d` | 相对当前时间 |
| `now` | `now` | 当前时间 |
| Unix 时间戳 | `1704067200`(秒) / `1704067200000`(毫秒) / 纳秒 | 按位数自动识别 |

示例：

```bash
# 最近 30 天，按天切片，4 并发
java -jar target/influxdb2tsfile-0.1.0.jar migrate \
  --url http://10.0.0.10:8086 --database telegraf --username admin --password admin123 \
  --start -30d --end now --time-slice 1d --parallel 4 \
  -o /data/tsfile/telegraf --verify

# 只迁移两个 measurement，大切片、压缩用 ZSTD
java -jar target/influxdb2tsfile-0.1.0.jar migrate \
  --url http://10.0.0.10:8086 --database telegraf --username admin --password admin123 \
  --measurements cpu,mem --time-slice 7d --parallel 2 --compression ZSTD \
  -o /data/tsfile/cpu_mem

# InfluxDB 2.x（Token 认证）
java -jar target/influxdb2tsfile-0.1.0.jar migrate \
  --url http://10.0.0.20:8086 --database telegraf --token my-token \
  --start 2023-01-01T00:00:00Z --time-slice 1d --parallel 4 -o /data/tsfile/telegraf2
```

### 5.4 `discover`：探查与评估

| 参数 | 说明 |
| --- | --- |
| `--measurements` / `--measurement-regex` / `--ignore-case` | 与 migrate 相同 |
| `--counts` | 额外统计每个 measurement 的点数（按其第一个 field 计数，是近似值；会扫数据，较慢） |
| `--json` | 以 JSON 输出到 stdout |
| `--report <file>` | 把 JSON 报告写入文件 |

```bash
java -jar target/influxdb2tsfile-0.1.0.jar discover --url http://10.0.0.10:8086 --database telegraf \
  --username admin --password admin123 --counts
# 输出示例
# server: 1.8.10 (OSS) at http://10.0.0.10:8086
# database: telegraf, retention policy: autogen
# measurements: 4 in total, 4 to migrate
#   cpu -> table cpu
#     tags:   host, region, zone
#     fields: cores(INT64), online(BOOLEAN), usage_idle(DOUBLE), usage_user(DOUBLE)
```

### 5.5 `lp2tsfile`：离线 line protocol 转 TsFile

用法：`lp2tsfile <file|dir|-> [选项]`，其中 `-` 表示从标准输入读取（会先落盘到临时文件，需要磁盘空间）；传入目录时只扫描其中的 `*.lp`、`*.txt`、`*.lineprotocol` 文件。

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `--precision` | `ns` | 输入时间戳精度：`s/ms/us/ns` |
| `--default-time` | 无（报错） | 没有时间戳的行使用该时间（如 `now`） |
| `--skip-invalid` | 否 | 跳过非法行而不是中断 |
| `--dry-run` | 否 | 只打印计划 |
| `--manifest` | `<out>/manifest.json` | 清单文件 |

行为说明：

- 会**先完整扫描一遍文件**建立 schema（行数/类型/标签），再写第二遍，所以输入文件需要一个稳定可读的路径（stdin 会先落盘）；
- 非法行（缺 field、字符串未加引号等）默认**报错中断**并指出文件与行号，可用 `--skip-invalid` 跳过（会统计并打印前 5 条示例）；
- 一个输入文件（或一次调用的多个文件）产生一组表：文件内所有 measurement 都写进同一个 tsfile 分片序列。

```bash
java -jar target/influxdb2tsfile-0.1.0.jar lp2tsfile /backup/telegraf.lp -o /data/tsfile/backup
java -jar target/influxdb2tsfile-0.1.0.jar lp2tsfile /backup/lp-dir -o /data/tsfile/backup --precision ns
cat /backup/telegraf.lp | java -jar target/influxdb2tsfile-0.1.0.jar lp2tsfile - -o /data/tsfile/backup
```

### 5.6 `inspect`：查看与校验 TsFile

用法：`inspect <file|dir> [选项]`

| 参数 | 说明 |
| --- | --- |
| `--rows N` | 每个表额外打印前 N 行 |
| `--json` | JSON 输出 |
| `--manifest <file>` | 与清单比对行数/文件是否齐全，不一致时退出码为 1 |

```bash
java -jar target/influxdb2tsfile-0.1.0.jar inspect /data/tsfile/telegraf --rows 3
# 输出示例
# file: cpu_00000-p0000.tsfile  (21.53 KB)
#   rows=1440, devices=4, range=[2024-01-01T00:00:00Z, 2024-01-01T05:59:00Z]
#   table cpu: rows=1440, devices=4, range=[...]
#     columns: host(TAG/STRING), region(TAG/STRING), zone(TAG/STRING), cores(FIELD/INT64), ...
#     time=2024-01-01T00:00:00Z, host=host-a, region=cn, zone=, cores=8, usage_idle=90.5, ...
```

## 6. 典型场景操作指南

### 6.1 阿里云 InfluxDB® 版退市迁移（1.x 兼容接口）

时间线提醒（阿里云公告）：

| 时间 | 状态 |
| --- | --- |
| 2025-10-23 | 停止新购 |
| 2026-04-23 | 不再提供续费和扩容 |
| 2026-10-23 | 正式退市，控制台关闭、实例释放 |

建议在 **2026-04-23 之前**完成迁移（之后无法扩容，实例一旦欠费/释放就再也拿不到数据），最迟不要晚于 2026-10-23。

操作步骤：

1. 确认可以从执行机访问实例（白名单/安全组放通 8086 端口），并拿到读写用的用户名密码；
2. 先跑 `discover` 看 schema 与数据量，估一下产物大小与耗时：

   ```bash
   java -jar target/influxdb2tsfile-0.1.0.jar discover \
     --url http://xxx.influxdb.rds.aliyuncs.com:8086 --database telegraf \
     --username admin --password *** --counts --report /tmp/plan.json
   ```

3. `--dry-run` 看一眼切片计划；
4. 正式迁移（建议 nohup 后台 + 日志 + `--verify`）；
5. 完成后用 `inspect --manifest` 校验，把产物目录 + manifest.json 一起归档。

如果实例已经释放/无法访问，走第 6.4 节的离线迁移（前提是之前用 `influxd backup/export` 或 `influx export` 导出过数据）。

### 6.2 InfluxDB 2.x 迁移

InfluxDB 2.x 的数据模型是 org/bucket/measurement，本工具通过 **InfluxQL 兼容接口**（`/query`，`db=<bucket>`）读取，因此需要 bucket 有对应的 DBRP 映射。InfluxDB 2.x 会自动为每个 bucket 建一条 `<bucket>/autogen` 的映射；如果没有，用 `influx` CLI 创建：

```bash
# 1) 找到 bucket id
influx bucket list --org myorg --token my-token

# 2) 建立 DBRP 映射（db 名 = bucket 名）
influx v1 dbrp create \
  --db telegraf --rp autogen --bucket-id 0123456789abcdef \
  --default --org myorg --token my-token
```

然后迁移：

```bash
java -jar target/influxdb2tsfile-0.1.0.jar migrate \
  --url http://127.0.0.1:8086 --database telegraf --token my-token \
  --start 2022-01-01T00:00:00Z --end now \
  --time-slice 1d --parallel 4 -o /data/tsfile/telegraf --verify
```

若查询报 `database not found`，就是缺 DBRP 映射，按上面创建后重试。

### 6.3 分批 / 反复执行 / 增量

- **相同参数的重复执行是幂等的**：每个工作单元在写入前会先删除自己名下（`<prefix>-<unit>-p*.tsfile`）的分片文件再重写，不会产生重复行；
- 换一套 `--start/--end/--time-slice` 会得到不同的单元名与文件，历史批次不会被覆盖；因此**不同批次建议放到不同输出目录**，或者用 `--file-prefix` 区分；
- 增量迁移的常见做法：老数据用一次大批量 + `--time-slice 7d`；日常增量用 `--start -2d --end now` 定期执行（用同一个目录会新增小文件，此时建议用单独目录避免碎片）。

### 6.4 离线迁移（line protocol）

InfluxDB 自带导出能力，可以在实例还能访问时先把数据导成 line protocol：

```bash
# 1.x：导出全量数据（分片导出更稳）
influxd backup -portable -database telegraf /backup/influxdb
# 或按 measurement 用查询导出为行协议
influx -database telegraf -execute 'SELECT * FROM cpu' -format csv > cpu.csv

# 2.x：导出为行协议
influx export all --org myorg --file /backup/export.json      # 元数据
influx query 'from(bucket:"telegraf") |> range(start: 1970-01-01T00:00:00Z)' --raw > telegraf.lp
```

拿到 `.lp` 文件后：

```bash
java -jar target/influxdb2tsfile-0.1.0.jar lp2tsfile /backup/telegraf.lp -o /data/tsfile/telegraf
```

注意：

- line protocol 必须是**合法格式**（字符串值要加双引号、tags 与 fields 之间要有空格、时间戳单位默认纳秒），非法行会报错并给出行号，确认可以跳过时加 `--skip-invalid`；
- 如果导出时用了非纳秒精度（例如 `--precision=ms`），迁移时用 `--precision ms` 保持一致。

### 6.5 大数据量调优

| 目标 | 手段 |
| --- | --- |
| 提升吞吐 | 提高 `--parallel`（4~8），提高 `--chunk-size`（50000~200000，减少往返） |
| 控制内存 | 减小 `--time-slice`、`--max-buffered-rows`、`--batch-size`；或降低并发 |
| 单文件过大 | 调小 `--max-file-size`（例如 512MB）；读取端按文件并行更友好 |
| 提高压缩率 | `--compression ZSTD`（CPU 换空间），或 `--compression SNAPPY/GZIP` |
| 慢查询超时 | 调大 `--query-timeout`，并把 `--time-slice` 调小 |
| 高基数（series 很多） | 保证 tag 列不被删除；`--max-buffered-rows` 调小，避免缓存太多设备；必要时按 measurement 分批迁移 |
| JVM | 默认 `-Xmx2g`（启动脚本），大并发建议 `-Xmx8g` 或更高 |

参考口径（单机、万兆内网、InfluxDB 1.8、4 并发、切片 1d）：稳定在 **3 万~10 万 点/秒**量级，具体取决于字段数量、series 基数与 InfluxDB 自身查询性能。可以先跑 1 天数据做基准，再推算总时长。

### 6.6 中断恢复

- 任何单元失败（网络抖动、查询超时、源端限流）都会记录到 manifest 的 `status: "failed"` 与 `error` 字段；
- 重新执行同样的命令并加 `--resume`，已完成的单元会被跳过，失败/未完成的单元重新迁移（会先清掉该单元的残留分片，避免半截数据与重复行）；
- `kill -9` 强杀也没问题：最多丢失「最后一个正在写入的单元」，重跑即可。

```bash
# 第一次（中途失败/被杀）
java -Xmx4g -jar target/influxdb2tsfile-0.1.0.jar migrate ... --time-slice 1d --parallel 4 -o /data/tsfile/telegraf
# 继续
java -Xmx4g -jar target/influxdb2tsfile-0.1.0.jar migrate ... --time-slice 1d --parallel 4 -o /data/tsfile/telegraf --resume --verify
```

`--resume` 要求参数中的 `--start/--end/--time-slice` 与上次一致（否则单元名对不上）。manifest 与产物必须在同一个输出目录。

### 6.7 数据校验

三个层次：

1. **写入时自校验**：`--verify` 回读所有分片，按表统计行数并与 manifest 比对；
2. **独立校验**：`inspect <dir> --manifest <dir>/manifest.json`，可在任意时间重复执行；不一致时退出码 1；
3. **与源端对账**：在 InfluxDB 侧统计每条 series 的点数，与 manifest 中该表的 `rows` / `devices` 对比。

源端统计示例（1.x）：

```bash
# 每个 measurement 的总点数（各 series 求和 = 迁移后的行数）
influx -database telegraf -execute 'SELECT COUNT(*) FROM cpu GROUP BY *' -format csv | wc -l
```

2.x：

```bash
influx query 'from(bucket:"telegraf") |> range(start: 1970-01-01T00:00:00Z) |> filter(fn:(r) => r._measurement == "cpu") |> group() |> count()'
```

产物侧统计：

```bash
java -jar target/influxdb2tsfile-0.1.0.jar inspect /data/tsfile/telegraf --json | python3 -c "
import json,sys
d=json.load(sys.stdin)
for f in d['files']:
    for t in f['tables']:
        print(f['file'], t['table'], t['rows'], t['devices'], t['minTime'], t['maxTime'])
"
```

## 7. 输出文件说明

### 7.1 文件命名

```
<out>/[<file-prefix>-]<unitId>-p<序号>.tsfile
```

- `unitId`：工作单元名 = 规范化后的 measurement 名；使用 `--time-slice` 时追加 `_00000`、`_00001` 等切片序号（从 0 开始，按时间从早到晚）；
- `序号`：同一个单元内触发滚动（超过 `--max-file-size` / `--max-rows-per-file`）时递增，从 `0000` 开始；
- 一个单元的数据**只**落在自己的文件里，不做跨单元混写，便于隔离、重跑与并行。

示例：

```
/data/tsfile/telegraf/
├── cpu_00000-p0000.tsfile      # measurement cpu 的第 1 个时间切片
├── cpu_00000-p0001.tsfile      #   ↑ 该切片超过 1GB，滚动出的第 2 个文件
├── cpu_00001-p0000.tsfile      # measurement cpu 的第 2 个时间切片
├── mem_00000-p0000.tsfile
├── weather_00000-p0000.tsfile
└── manifest.json
```

## 8. 读取生成的 TsFile

### 8.1 Java（TsFile SDK）

```xml
<dependency>
  <groupId>org.apache.tsfile</groupId>
  <artifactId>tsfile</artifactId>
  <version>2.4.0</version>
</dependency>
```

```java
import org.apache.tsfile.read.query.dataset.ResultSet;
import org.apache.tsfile.read.v4.ITsFileReader;
import org.apache.tsfile.read.v4.TsFileReaderBuilder;

import java.io.File;
import java.util.Arrays;

public class ReadExample {
  public static void main(String[] args) throws Exception {
    File file = new File("/data/tsfile/telegraf/cpu_00000-p0000.tsfile");
    try (ITsFileReader reader = new TsFileReaderBuilder().file(file).build();
        ResultSet rs =
            reader.query("cpu", Arrays.asList("host", "region", "cores", "usage_idle"),
                Long.MIN_VALUE, Long.MAX_VALUE)) {
      while (rs.next()) {
        long time = rs.getLong("Time");                       // 纳秒时间戳
        String host = rs.isNull("host") ? null : rs.getString("host");
        Long cores = rs.isNull("cores") ? null : rs.getLong("cores");
        Double idle = rs.isNull("usage_idle") ? null : rs.getDouble("usage_idle");
        System.out.println(time + " " + host + " " + cores + " " + idle);
      }
    }
  }
}
```

要点：

- 查询参数里的列名使用 **TsFile 里的列名**（小写、规范化后的名字）；
- 时间列固定叫 `Time`，单位纳秒；
- 一个表可能分布在多个文件中（多切片/多分片），需要遍历目录里所有 `*.tsfile` 并对每个文件查询，或使用支持通配的读取方式；同一设备的相邻时间片落在不同文件时，跨文件拼接按时间排序即可。

### 8.2 导入 IoTDB / TimechoDB

TsFile 是 IoTDB/TimechoDB 的原生格式，可通过 `load tsfile` 类工具导入；本工具生成的是**表模型**（table model），导入前请确认目标版本的加载要求（表模型、列名匹配）。若目标环境要求特定的表名前缀/列名，可在迁移时用 `--table-prefix`、`--no-sanitize`、`--field-type` 调整。

## 9. 常见问题（FAQ）

**Q1：discover 报 `no measurement matched`？**
database/bucket 名写错，或账号没有该库的读权限。先用 `discover` 不带 `--measurements` 看有哪些 measurement。

**Q2：连接失败 `cannot reach InfluxDB`？**
检查地址与端口（1.x 默认 8086）、网络/白名单、实例是否存活；HTTPS 自签证书需要把 `https://` 地址配好信任（可用 `-Djavax.net.ssl.trustStore` 指定信任库）。

**Q3：查询报 `field type conflict`？**
同一个 field 有多类型。用 `--type-conflict text`（转字符串）或先处理源数据；也可以 `--time-slice` 把时间切开后分批迁移。

**Q4：列名变了（大写变小写、点变成下划线）？**
TsFile 表模型列名不区分大小写，工具会做规范化并把原名记入 manifest。希望尽量保留原样时用 `--no-sanitize`（仍然会转小写），从 manifest 的 `source` 字段还原对应关系。

**Q5：为什么某些行某些列是 null？**
InfluxDB 允许同一 series 的不同时间点有不同的 field 集合，缺失的字段就是 null，属正常现象。

**Q6：能不能只迁移部分字段？**
可以，`--exclude-fields a,b`。被排除的字段不会出现在表结构里。

**Q7：能不能去掉 tag？**
用 `--exclude-tags` 可以，但**有风险**：tag 决定 series 身份，去掉后不同 series 的同一时间点会被合并（后者覆盖前者）。除非确认同一 measurement 内不会出现同时间戳的多 series，否则不要排除。

**Q8：迁移很慢怎么办？**
先确认瓶颈：`--log-level debug` 看单单元耗时。InfluxDB 单查询慢（大范围聚合/高基数）时，调小 `--time-slice`、提高 `--parallel`，并提高 `--query-timeout`。

**Q9：manifest.json 里出现 `failed` 单元怎么办？**
看 `error` 字段：多为查询超时/网络问题/类型冲突。修复原因后用同样的参数加 `--resume` 重跑，只会重做失败单元。

**Q10：产物太大或太小？**
`--max-file-size` 控制单文件上限（默认 1GB），`--compression` 控制压缩，ZSTD 通常最小但更耗 CPU。

**Q11：能迁移到同一个目录多次吗？**
同参数重跑幂等（覆盖同名单元文件）；不同时间切片会产生新文件。跨批次建议用不同目录或不同的 `--file-prefix`。

**Q12：无符号整数超范围？**
InfluxDB 的 unsigned 最大 18446744073709551615，超过 INT64 上限时该单元会失败并提示；这类字段建议用 `--field-type <field>=STRING`。

**Q13：支持多 RP（保留策略）吗？**
默认只迁移默认 RP；可以用 `--rp` 指定其它 RP 再单独迁一次（放到不同输出目录或加 `--table-prefix` 区分同名 measurement）。

**Q14：日志里 `unit xxx contains no row`？**
该时间片内确实没有数据，属正常（状态记为 `empty`，不计入失败）。

**Q16：执行命令时报 `UnsupportedClassVersionError` / `类文件具有错误的版本 61.0`？**
JDK 版本过低。Apache TsFile 2.4.0 的字节码是 Java 17（class file version 61.0），本工具要求 **JDK 17 及以上**。
这个错误有迷惑性：低版本 JDK 下 `--version`、`--help` 可能正常，执行 `migrate` / `lp2tsfile` / `inspect` 才报错。

```bash
java -version                      # 确认版本（需要 17+）
export JAVA_HOME=/path/to/jdk-17   # 或 21 / 25
bin/influxdb2tsfile --version      # 启动脚本会自检 JDK 版本并给出提示
```

若确实只能用 JDK 11，需要改用基于 TsFile 2.3.x（Java 8 字节码）的旧版本，2.4.0 不支持。
**Q15：迁移过程中源库还能写数据吗？**
可以。工具按时间范围只读；若迁移期间有新数据写入，可在迁移结束后用 `--start <上次的end>` 增量补一次。

## 10. 已知限制

1. 只读取 field/tag，不做 InfluxDB 的连续查询（CQ）、订阅（subscription）、任务等元数据迁移；
2. 一个 measurement → 一个表；跨库（database/bucket）同名表需要 `--table-prefix` 区分；
3. 默认只迁移默认 RP（1.x）；多 RP 需分别执行；
4. 非默认时间单位写入的数据（如微秒）在 InfluxDB 里仍以纳秒存储，本工具输出纳秒时间戳，不丢失精度；
5. 类型冲突字段需要用 `--type-conflict text` 或预处理；
6. TsFile 表模型列名大小写不敏感，存在大小写不同但同名的 key 时会被重命名（`_1` 后缀）并记录在 manifest；
7. 不生成 web 界面，不提供 HTTP 服务，只有命令行；
8. 迁移元数据（measurement/tag/field 的注释、权限等）不在范围内。
